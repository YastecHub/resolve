# resolve

resolve investigates disputed bank transactions. An AI agent reads the bank's records through read-only tools, explains what happened with cited evidence, and recommends an outcome. The bank's own rules decide whether the case can be settled automatically or needs an analyst, and every step is written to a tamper-evident audit trail.

Built by Team Phantasm for the Ogun Innovate Hackathon at the Ogun Digital Summit 2026, and deployed on Nobus Cloud.

## Why

A failed transfer or a double charge usually means days of a customer chasing their bank while someone in the back office checks five systems by hand. resolve does that investigation in about a minute and shows its working, so customers get their money back faster and the bank gets a record it can hand to a regulator.

## How it works

1. A bank channel files a dispute against a transaction.
2. The dispute waits in a queue, so spikes never drop a case.
3. The agent investigates: transaction, ledger, settlement, device and location, customer history, merchant, related payments. Personal data is masked before the model sees it.
4. The agent submits a decision where every claim cites a specific lookup. resolve checks the citations are real.
5. A policy engine with 11 rules decides: auto-resolve, or send to an analyst with the reasons.
6. Money moves only through a separate executor, once, atomically.
7. Every step is hash-chained, so editing the record afterwards is detectable.

The full picture is in [RESOLVE.md](RESOLVE.md).

## Stack

TypeScript throughout. NestJS with PostgreSQL (Prisma) and Redis (BullMQ) for the API and the investigation worker, React Router with TanStack Query and Tailwind CSS for the dashboard, any OpenAI-compatible model for the agent, Docker Compose on a Nobus Cloud VM behind nginx, and GitHub Actions for deployment.

## Getting started

You need Node.js 24, pnpm and Docker.

```
git clone https://github.com/YastecHub/resolve.git
cd resolve
```

### Run the whole stack

```
cp .env.example .env      # optional: change the database password
docker compose up -d --build
```

| What               | Where                               |
| ------------------ | ----------------------------------- |
| Dashboard          | http://localhost:5175               |
| API                | http://localhost:9000/api/v1        |
| Health             | http://localhost:9000/api/v1/health |
| API docs (Swagger) | http://localhost:9000/api/v1/docs   |

Compose starts PostgreSQL, Redis, the API and the dashboard. Postgres and Redis stay on the internal Docker network; the API and dashboard listen on `127.0.0.1` only.

### Develop

```
pnpm install
docker compose up -d postgres redis
DATABASE_URL=postgres://resolve:resolve@localhost:5432/resolve REDIS_URL=redis://localhost:6379 pnpm --filter api dev
pnpm --filter web dev      # http://localhost:5175, proxies /api to :9000
```

To reach Postgres and Redis from your machine during development, publish their ports with a `compose.override.yaml`.

| Command                      | What it does                                                     |
| ---------------------------- | ---------------------------------------------------------------- |
| `pnpm dev`                   | Run every workspace in development                               |
| `pnpm build`                 | Build every workspace                                            |
| `pnpm typecheck`             | Type-check every workspace                                       |
| `pnpm lint`                  | ESLint across the repo                                           |
| `pnpm test`                  | Unit tests                                                       |
| `pnpm --filter api test:e2e` | API end-to-end tests                                             |
| `pnpm api:generate`          | Export the OpenAPI document and regenerate `packages/api-client` |
| `pnpm format`                | Format everything with Prettier                                  |

### Deployment

Every push to `main` runs the checks in `.github/workflows/ci.yml` and, if they pass, deploys to the Nobus Cloud VM over SSH. See [ARCHITECTURE.md](ARCHITECTURE.md#deployment).
